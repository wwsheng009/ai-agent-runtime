## 1. 功能清单

按「用户能感知到什么」归纳，共 6 项能力：

| # | 功能 | 表现 | 限制 |
|---|---|---|---|
| F1 | **本地文件夹零拷贝挂载** | `@folder` 后沙箱内出现 `/mnt/local/<basename>`，直接读写本机真实文件 | 每会话最多 16 个 |
| F2 | **实时双向同步** | 本机改动沙箱立即可见，反向亦然；无快照、无延迟队列 | 依赖隧道在线 |
| F3 | **完整文件系统语义** | 读、写、建、删、改属性、目录遍历，`git` / `gcc` / `python` 免改造 | 每次操作一次网络往返 |
| F4 | **最小授权粒度** | 仅代理被显式引用的那一个目录；沙箱无法访问其父目录或其它盘符 | 挂载点为读写，非只读 |
| F5 | **凭证零下发** | 沙箱内不存在 Windows 账号、磁盘凭据、SMB 口令 | — |
| F6 | **崩溃自愈** | s6 监督下 worker 崩溃自动拉起 | 拉起后需客户端重连 |

**非功能（明确不做）**：不做数据复制上传、不做 NFS/CIFS/9p 共享、不做版本快照与回滚、不做本地数据缓存。

## 2. 逻辑架构：三层职责

```
用户电脑 (Windows)                    沙箱虚拟机 (Linux)
─────────────────────                 ────────────────────────────────
本地磁盘真实读写                       VFS / fuse 驱动
      ▲                                      ▲
      │                                      │ /dev/fuse
客户端隧道模块                         tabbit-fuse (用户态 FS)
      │                                      │
      └──── WebSocket 长连接 :19780 ─────────┘
             （由客户端主动发起，经云端中继）
```

| 层 | 组件 | 唯一职责 | 明确不负责 |
|---|---|---|---|
| 客户端层 | Tabbit 客户端桥接模块 | 把 RPC 翻译为对本地磁盘的真实系统调用；只暴露授权目录 | 不缓存、不落盘副本 |
| 守护进程层 | `tabbit-fuse` | 文件系统语义 ↔ RPC 消息的双向翻译；路径映射；超时控制 | 不触碰真实数据存储 |
| 内核层 | VFS + fuse 驱动 | 让挂载点对所有进程表现为普通目录 | 不感知远端存在 |

**为什么必须是反向连接**：沙箱在 NAT 与防火墙之后，无公网可达地址；用户电脑也不应开放入站端口。因此方向倒置为「本机主动出站连沙箱」，穿透 NAT，且客户端只代理单一授权目录。

## 3. 逻辑主线：一次文件访问怎么走

以沙箱内 `cat /mnt/local/<folder>/VERSION` 为例：

```
① open() 系统调用
② VFS 按路径匹配挂载点
③ fuse 驱动打包 FUSE 消息 → /dev/fuse
④ tabbit-fuse 解析出相对路径，映射到远程根，启动 30s 计时
⑤ 序列化 RPC → 经 WebSocket 发出
⑥ 客户端拼接本地真实路径 → 执行真实文件 API
⑦ 结果（句柄号/数据/errno）回传
⑧ tabbit-fuse 写回 /dev/fuse
⑨ 内核返回给 shell
```

**关键逻辑点：一次 `cat` 不是一次 RPC，而是多个独立操作各自往返。**

| FUSE 操作 | 语义 | 走隧道 |
|---|---|---|
| `LOOKUP` | 路径名 → inode | ✅ |
| `GETATTR` | size / mode / mtime | ✅ |
| `OPEN` | 打开并协商标志 | ✅ |
| `READ` | 按 128 KiB 分块 | ✅ 每块一次 |
| `WRITE` | 按块写入 | ✅ 每块一次 |
| `CREATE` / `MKDIR` / `UNLINK` | 新建 / 建目录 / 删除 | ✅ |
| `FLUSH` / `FSYNC` | 刷缓存到持久存储 | ✅ |
| `RELEASE` | 关闭句柄 | ✅ |

**由此推出两条必须记住的结论**：

1. **元数据也走隧道**，所以隧道断开时连 `ls`、`stat` 都会失败，不只是读不到内容。
2. **延迟来自往返次数，不是带宽**。目录遍历、`grep -r`、大文件顺序读都是往返密集操作。

## 4. 生命周期

```
[1] 用户 @ 提及文件夹 → 客户端向平台登记授权（路径 + mount id + 沙箱侧路径）
[2] 平台在沙箱内准备挂载
[3] tabbit-fuse 轮询 envd /health 直至 204（就绪前置）
[4] 客户端发起 TCP + WebSocket 握手 → :19780 建立长连接
[5] 在 --mount-base 下创建挂载点，命名 = 本地文件夹 basename
[6] 挂载生效，沙箱内可访问
[7] 会话结束 / 取消引用 / 连接断开 → 卸载并清理挂载点
```

**命名规则带来的逻辑后果**：挂载点取 basename 而非完整路径，因此 `D:\a\proj` 与 `E:\b\proj` 会争用同一挂载点 `/mnt/local/proj`。这正是 `mount id` 必须作为独立标识存在的原因——仅靠路径无法区分同名目录。

**就绪依赖的逻辑意义**：`--ci-health-url` 指向 `envd` 的 `/health`。文件挂载能力与 code-interpreter 服务（49999）**解耦**，后者异常不阻塞挂载就绪。

## 5. 运行参数与限制

### 5.1 守护进程参数（实测运行值）

| 参数 | 运行值 | 逻辑作用 |
|---|---|---|
| `--listen` | `0.0.0.0:19780` | WebSocket 监听地址，隧道入口 |
| `--mount-base` | `/mnt/local` | 挂载点父目录，一文件夹一子目录 |
| `--max-mounts` | `16` | 并发挂载上限 |
| `--max-read-bytes` | `1048576`（1 MiB） | 单次读 RPC 消息体上限 |
| `--max-write-bytes` | `1048576`（1 MiB） | 单次写 RPC 消息体上限 |
| `--op-timeout` | `30s` | 单 FUSE 操作超时（帮助默认 10s） |
| `--ci-health-url` | `http://127.0.0.1:49983/health` | 就绪前置探针 |
| `--ci-health-timeout` | `2s` | 探针超时 |

### 5.2 挂载选项（内核侧）

```
tabbit-localfs /mnt/local/<folder> fuse.tabbit
    rw,nosuid,nodev,relatime,user_id=0,group_id=0,allow_other,max_read=131072
```

| 选项 | 逻辑含义 |
|---|---|
| `fuse.tabbit` | 私有 FUSE 子类型，可据此精确识别本能力 |
| `tabbit-localfs` | 设备源仅作标识，无真实块设备 |
| `rw` | 读写，非只读映射 |
| `nosuid,nodev` | 阻断经该挂载提权（suid 二进制、设备节点注入） |
| `allow_other` | 沙箱内其他用户/进程亦可访问 |
| `user_id=0,group_id=0` | 属主为 root；实际权限由隧道对端决定 |
| `max_read=131072` | 单次读请求上限 128 KiB |

### 5.3 一处必须注意的参数不一致

内核 `max_read=131072`（128 KiB）**小于**守护进程 `--max-read-bytes=1048576`（1 MiB）。**实际单次往返以更紧的 128 KiB 为准**，守护进程的 1 MiB 在当前配置下不会被吃满。评估性能时应按 128 KiB 建模。

### 5.4 性能模型

| 约束 | 数值 | 直接影响 |
|---|---|---|
| 单块读取 | 128 KiB | 读 100 MB ≈ 800 次往返 |
| 单操作超时 | 30 s | 大目录递归遍历易触发 |
| 并发挂载 | 16 | 超出无法新增 |
| 数据缓存 | 无（纯代理） | 重复读同一文件仍走隧道 |
| 延迟来源 | 到中继节点 RTT | 跨地域时元数据密集操作显著变慢 |

实测参照：读约 11 KB 文件耗时 ~0.26 s，同尺寸本地文件通常 1 ms 量级——差距来自进程启动 + 上下文建立 + 网络往返。

**适用性判断**：
- ✅ 适合：读源码、改配置、小文件增删、`git` 操作（对象多但单文件小）。
- ❌ 不适合：`node_modules` 全量扫描、大二进制读写、数据库文件、频繁随机 IO、全仓库 `grep -r`。
- 💡 建议：重 IO 前先 `cp` 到 `/mnt/work`（沙箱本地盘），避免每步跨隧道。

## 6. 安全逻辑

| 边界 | 机制 | 评价 |
|---|---|---|
| 授权范围 | 仅显式 `@` 的单个目录 | ✅ 最小权限 |
| 提权面 | `nosuid,nodev` | ✅ 阻断 suid / 设备节点 |
| 凭证隔离 | 沙箱无 Windows 凭据 | ✅ 仅一条受限隧道 |
| 网络暴露 | 用户侧仅出站，不开入站端口 | ✅ NAT 后可用 |
| 身份映射 | root 属主 + `allow_other` | ⚠️ 沙箱内任意进程可访问 |
| 写入风险 | `rw` 读写 | ⚠️ `rm -rf` 真实作用于用户磁盘 |
| 传输加密 | WebSocket（通常 wss） | ⚠️ TLS 终止位置未在沙箱内验证 |
| 中继可见性 | 流量经 `10.133.x.x` | ⚠️ 若中继终止 TLS，则中转侧可见文件内容 |

**两条必须传达给使用者的逻辑结论**：

1. **`allow_other` + root 属主 ⇒ 授权目录对沙箱内所有代码（含不受信代码）完全可见**。目录内含 `.env`、SSH 私钥、密钥文件时，等同于交给沙箱。
2. **读写而非只读，且无快照兜底**。一次误删除不可回滚。重要目录应先确认 Git 可恢复性，或改用只读授权（若平台支持）。

## 7. 与命令通道的逻辑关系

两条隧道**物理隔离**，这是故障隔离设计而非实现巧合：

| 维度 | 命令通道 | 文件挂载通道 |
|---|---|---|
| 守护进程 | `envd` | `tabbit-fuse` |
| 端口 | `49983` | `19780` |
| 协议 | Connect / gRPC-over-HTTP | 自定义 RPC（WebSocket 帧） |
| 传输内容 | 命令参数、stdout/stderr、exit_code | 文件字节、元数据 |
| 故障影响面 | 命令全部不可执行 | 本地目录不可访问（沙箱本地盘正常） |
| 依赖关系 | 独立 | 依赖 `envd` `/health` 作就绪前置 |

**实测佐证**：文件通道报 `EIO` 期间，命令通道持续正常。说明二者不是同一连接上的多路复用。

**单向依赖的逻辑含义**：文件挂载依赖 envd 就绪，但 envd 不依赖文件挂载。因此 envd 故障会连带挂载不可用，反之不成立。

**与 virtiofs 的分工**：`/mnt/cos/*`、`/mnt/skill-state` 等走 virtiofs（要求共享目录在虚拟机宿主侧）；用户目录在个人电脑上，与宿主是不同机器，**只能走网络隧道**——这是必须自建 FUSE 而不能复用内核文件系统的根本原因。

## 8. 已知缺陷：`close` 阶段间歇性 EIO

**现象**：内容正确读出，但收尾阶段返回 `Input/output error`；连续重试结果一致（非偶发抖动）。`cat` 输出完整但退出码异常。

**逻辑定位**：错误发生在 `RELEASE` / `FLUSH`，而非 `OPEN` / `READ`。**数据通路是通的，缺陷在收尾环节。**

**可能根因（待官方确认，按可能性排序）**：
1. 隧道侧对 `RELEASE` 响应丢失或未回包，超时后由 FUSE 层报 `EIO`；
2. 客户端处理 Windows 句柄关闭时返回非预期错误码；
3. `FLUSH` 语义映射缺失（Windows 无完全对等的 flush-on-close 语义）。

**影响面（这是本条最需要警惕的部分）**：
- ✅ 不影响读到的内容本身；
- ❌ 让 `cat` / `head` 返回非零退出码，**可能误伤依赖退出码的脚本与 CI 判定**；
- ❌ 编辑器保存、`git` 写入后校验可能因 close 失败而回滚或报错。

**规避方式**：显式限定字节数（`dd bs=... count=...`）；脚本内不因 close 失败中断（`cmd 2>/dev/null || true`）；需要可靠处理时先复制到 `/mnt/work`。

> 该异常不代表挂载不可用——目录遍历、`stat`、写入、`mkdir`/`rmdir` 均实测成功。

## 9. 运维与排障

| 症状 | 逻辑原因 | 诊断 | 处置 |
|---|---|---|---|
| `Input/output error` | 隧道断开 / 重连中 | 查 19780 是否有 ESTAB 连接 | 等自动重连，或重新 `@` 引用 |
| 挂载点不存在 | 未建立或已卸载 | `ls /mnt/local` | 重新引用文件夹 |
| 读取极慢 | RTT 高 / 大文件 / 往返密集 | 观察文件大小与操作类型 | 先拷到 `/mnt/work` |
| 操作超时 | 单操作超 30 s | 是否大目录递归 | 缩小操作粒度 |
| 新文件夹挂不上 | 已达 16 个上限 | `ls -d /mnt/local/*/ \| wc -l` | 取消部分引用 |
| 挂载点名字冲突 | basename 相同 | 检查目录名 | 重命名其一 |
| 写入后本机未见 | 缓存未刷 / 隧道延迟 | 重读确认 | 显式 `sync` 或重试 |
| 只有 close 报错 | §8 已知缺陷 | 看退出码与输出是否分离 | 用规避写法 |

诊断命令：

```bash
grep "/mnt/local" /proc/self/mounts          # 挂载状态
ss -tnp | grep 19780                         # 隧道连接
ps -eo pid,args | grep tabbit-fuse           # 守护进程
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:49983/health   # 期望 204
stat /mnt/local/<folder>/<file>              # 只查元数据，绕过数据通道
```

## 11. 小结

这套功能的本质是一次**语义降级再重建**：把 Windows 本地磁盘的文件系统语义降级为可跨网络传输的 RPC 消息流，再在 Linux 沙箱内用 FUSE 重建为目录树。

**换来**：数据不出本机、授权粒度到单文件夹、零客户端安装成本。
**代价**：每个 IO 都是网络往返；连接断开时整个目录瞬间失效（单点依赖）；close 阶段存在已知缺陷。

正确的使用心智：把它当作「挂在网络另一端的薄代理」——小文件编辑与源码阅读很顺手，重 IO 与大文件处理应先落到沙箱本地盘。
