## 1. Why WSL

The Windows host had previously been memory-constrained while running the
backend test/build surface. WSL gives the same source tree a Linux environment
with its own Go build cache and enough memory, and it matches the production
shape (Linux amd64) for the remote-tools client.

WSL has no `pwsh`, so the existing
`scripts/canary-remote-tools.ps1` cannot run inside WSL. The new
`backend/scripts/remotetools_canary.go` is the Linux-native equivalent: it uses
the same `modelcontextprotocol/go-sdk` client dependency as the product, reads
the token without printing it, and only exercises read tools plus one
allowlisted `git` command.

### 6.3 `aicli chat --remote` connection

```bash
aicli --mesh=false chat --no-interactive --headless --stream=false --output json \
  --remote 'http://172.18.3.238:18765' --permission-mode plan \
  --prompt 'Use remote_238__view to read README.md with limit 5 ...'
```

The remote half succeeded:

```text
remote: added server "172-18-3-238" (transport=streamable, requested profile=readonly); tool names come from the target's own toolPrefix
```

The model half then failed before any tool call:

```text
{"ok":false,"command":"chat","error":"操作错误: provider call failed after repeated fast-fail retries: provider transport call failed after retries: failed to send request: Post \"http://127.0.0.1:18900/v1/chat/completions\": dial tcp 127.0.0.1:18900: connect: connection refused"}
```

This is **BLOCKED**, not a product failure: the WSL-side `free_models` provider
listens on the Windows loopback (`127.0.0.1:18900`), which is not reachable from
WSL. The `--remote` server connection itself was established and named the
target correctly.
