## 1. 目标与范围

### 1.1 目标

把 crush 中已被验证有效的 LSP 接入模式，翻译为 ai-agent-runtime 可实施的**分层设计**：

1. **同一 tool call 内闭环**：编辑类工具执行后，在同一次返回中附上诊断，模型无需额外往返即可感知"我改坏了什么"。
2. **诊断作为一等工具输出**：`lsp_diagnostics` 不是旁路日志，而是进入模型上下文的工具结果。
3. **可降级**：LSP 不可用（未安装/启动失败/超时）时，工具调用本身必须仍然成功，只是少一段诊断文本。
4. **可归因**：每个诊断能回答"来自哪个 server、针对哪个文件、属于本次改动还是项目既有问题"。

### 1.2 明确不做（边界表）

| 不做的事 | 事实源 / 理由 |
| --- | --- |
| 不定义 core schema、本目录不新增表列 | 落入 `03_agent_harness_supplement.md` §5.2 既有列 `lsp_diagnostics` / `lsp_servers`；上游已授权的列（ADR-0006 的编码列）按 Gate 生效，本文不自行增列 |
| 不定义位置编码转换规则 | `adr/0006-lsp-position-encoding-boundary.md` |

| Phase 0–3 期间不落代码 | 见 `README.md` §4，最早起点 `Phase4-start` |

## 2. 分层（核心章节）

参考实现里 LSP 与 agent 的关系可以拆成 6 层。下表把 **crush 的做法**、**本项目的落点**、**事实源** 三列对齐。

| # | 层 | 职责 | crush 的做法 | 本项目的落点 |
| --- | --- | --- | --- | --- |
| L1 | 归属层 | 谁拥有 LSP 进程、如何与 ACP 会话绑定 | 进程内 `*csync.Map[string, *lsp.Client]` 共享给工具 | 显式建模，遵 `adr/0002` |
| L2 | 生命周期层 | 启动、健康检查、重启、降级 | `initLSPClient` 失败仅记日志 + 状态标记，不阻断 | 同构；状态可观测 |
| L3 | 路由层 | 判断某文件由哪个 server 负责 | `client.HandlesFile(path)` | 同构 |
| L4 | 同步层 | `didOpen/didChange/didSave` 与位置编码 | 编辑后 `notifyLSPs` | 同构，编码策略遵 `adr/0006` |
| L5 | 工具层 | 诊断的获取与绑定 | `getDiagnostics` + 编辑工具内联 | 同构，见 §3 |
| L6 | 呈现/持久层 | 诊断文本格式与落库 | 拼接为文本追加到 tool result | 既有列 `lsp_diagnostics` / `lsp_servers` |

### 2.1 L1 归属层

crush 是单进程 CLI，LSP client 集合在进程内共享，归属问题被"进程即会话"掩盖了。

本项目是多进程 + ACP 结构，**归属必须显式建模**：谁 spawn LSP、LSP 生命周期跟随 ACP 会话还是跟随工作区、多个 ACP 会话是否共享同一 LSP 实例。这些问题在 `adr/0002-acp-lsp-ownership.md` 中裁定，本文只做**接口假设**：

- 工具层只依赖一个抽象的 `LSPRegistry`，不关心背后是进程内还是跨进程。
- `LSPRegistry` 必须能回答 L3 的路由问题，并能对不可用 server 返回"无诊断"而不是错误。

### 2.2 L2 生命周期层

从 01 §6.2 的一条关键事实推广：**LSP 启动失败是常态，不是异常**。因此：

- 启动失败 → 记录状态 + 日志，工具继续可用。
- 运行中崩溃 → 标记该 server 为不可用，后续 `getDiagnostics` 跳过它。
- 重启策略（自动/手动）属于实现细节，但**必须可观测**：`lsp_servers` 列要能表达"哪些 server 当前可用、哪些失败、失败原因"。

### 2.3 L3 路由层

一个文件可能被多个 server 覆盖（例如 tsserver 与 eslint）。crush 的 `HandlesFile` 是"逐 server 询问"，本项目保持同构，但要求：

- 路由判定基于**文件路径 + 语言/扩展名/项目标记**，不使用文件内容启发式。
- 未被任何 server 覆盖的文件 → 直接返回空诊断，零开销。

### 2.4 L4 同步层

编辑类工具在返回前必须把变更同步给 LSP，方式是 `didChange`（或 `didSave`），使 server 内部状态与磁盘一致。

**位置编码边界**：LSP 用 UTF-16 code unit 计数，运行时内部用字节或 rune。转换只能发生在**同步层这一处**，不允许工具层或呈现层各自转换。具体规则见 `adr/0006-lsp-position-encoding-boundary.md`。

### 2.5 L5 工具层

这是 crush 模式最有价值的一层，也是本文 §3 展开的重点。

### 2.6 L6 呈现/持久层

- 呈现：诊断拼成文本追加到 tool result 尾部（crush 的做法），格式需稳定、可解析、对模型友好。
- 持久：写入既有列 `lsp_diagnostics`、`lsp_servers`，**本目录不新增列**。
- 阈值（条数上限、字符预算、是否只保留本次改动相关诊断）**不写死**，作为配置项并进入 `03` 验收。

## 3. 关键设计：把诊断闭环塞进同一次 tool call

这是 01 章分析出的**唯一"必须照抄"的行为**，也是本设计与"事后拉诊断"方案的分水岭。

### 3.1 crush 的时序

```
执行编辑 → 若 IsError 直接返回 → notifyLSPs(file) → text += getDiagnostics(file) → 返回 text
```

要害有两点：

1. **追加，不是替换。** 编辑成功的原始返回文本一字不动，诊断附在尾部。模型不会因为多了诊断而丢失"我改了什么"的事实。
2. **同一次 tool call 内返回。** 模型不需要额外发起一次 `diagnostics` 调用来发现自己刚写的语法错误。反馈环闭合在一次 LLM 轮次内。

### 3.2 本项目的落点

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 是否在编辑类工具内联诊断 | **是** | 反馈环闭合，省一轮 LLM 往返 |
| 追加还是替换原文 | **追加** | 同 3.1-1，且便于后续解析 |
| 编辑失败时是否附带诊断 | **否**（直接返回错误） | 编辑未生效，诊断无意义且污染信号 |
| 非编辑类工具是否附带 | 默认否，按需 | 避免每次读文件都拖一堆诊断 |
| 无 LSP 覆盖该文件时 | 静默跳过，不报错 | L2 降级策略 |

### 3.3 必须配套的两个前提

- **L4 同步层必须先于诊断生效**：编辑落盘后要 `didChange`/`didSave`，否则 LSP 侧看到的仍是旧文本，诊断会是"上一版的错误"。crush 用 `notifyLSPs` 显式做这件事，本项目不可省略。
- **诊断必须能定位到"本次改动引入的"**：crush 直接全量返回该文件诊断。全量在文件本身已是脏的时候会给模型噪声。是否引入 baseline 差分 **不在此拍板**，进 `03` 验收（见 §6）。

## 4. 工具面设计

参考实现的工具面很薄：一个诊断工具 + 编辑工具的隐式内联。本项目保持同样的克制。

### 4.1 工具清单（映射到 crush）

| 工具 | crush 对应 | 职责 | 是否新增 |
| --- | --- | --- | --- |
| `diagnostics` | `internal/agent/tools/diagnostics.go` | 主动拉取某个文件/项目的诊断 | 复用既有工具位 |
| 编辑类工具内联诊断 | `edit.go` 尾部追加 | 见 §3 | 行为增强，非新工具 |
| LSP 重启/状态 | `lsp_restart.go` | 服务异常时的恢复入口 | 复用 |
| 引用查找 | `references.go` | 符号引用 | 复用 |

**关键约束：不为了 LSP 新开一个平行的工具家族。** 工具应当是"既有工具在 LSP 可用时的增强"，否则会出现"有 LSP 用 A 工具、没 LSP 用 B 工具"的分裂，模型侧提示词成本翻倍。

### 4.2 模型可见提示词

crush 在 `internal/agent/tools/diagnostics.md` 的 `<tips>` 里写了：

```
- Use with other tools for comprehensive code review
- Combine with LSP client for real-time diagnostics
```

两条都是**行为引导**，而非接口说明。本项目的提示词需要覆盖三点：

1. 何时主动调 `diagnostics`（改完一批、跨文件改动后）；
2. 编辑返回里附带的诊断是**同一文件、当前版本**的，可以直接采信；
3. LSP 不可用时的降级预期（不要因为拿不到诊断就反复重试）。

第 3 点是 crush 作为本地 CLI 可以不写、而本项目必须写的——多会话/远程场景下 LSP 缺失是常态而非异常。

### 6.3 与 crush 的刻意差异（必须承认）

| 维度 | crush | 本项目 | 原因 |
| --- | --- | --- | --- |

## 7. 结论

1. crush 的 LSP 用法中，**唯一不可省略的关键动作**是：编辑工具在返回前完成 `didChange/didSave` 同步并把当前版本诊断内联进返回体——这让模型在一次工具调用内就拿到"我改坏了什么"。
2. 本项目的接入应当**沿用这一形态**，并在三处做本地化：提示词的降级说明、等待时延上限、诊断噪声控制。
3. 数据一律落既有列（`lsp_diagnostics` / `lsp_servers`）；**本目录不自行增列**——编码列由 ADR-0006 授权（`Phase4-start` Gate），归属与编码规则遵守 ADR-0002 / ADR-0006。
4. 所有未决问题（Q1–Q5）不在本文拍板，移交 `03` 验收回路。

**下一步：见 `03-implementation-plan-and-acceptance.md`（排期、阶段门禁、验收清单）。**
