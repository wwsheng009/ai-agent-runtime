## 一、结论

控制台的壳层结构、暗色主题、主任务入口总体成立，**不存在“整套界面不可用”的系统性崩坏**。经过复核，原稿中的问题可收敛为：

- **1 个已修复待回归 P0**：「待处理」已与 `completed` / `waiting` 解耦，等待真机回归。
- **0 个待处理 P1 + 5 个已实施待回归 P1**：通知设置、窄屏页头、长文本、会话失败路径与卡片操作模型均已在 `v63` 修复，等待浏览器/真机回归。
- **3 个已实施待回归 P2**：危险操作层级、信息架构冗余、可访问性代码层均已在 `v68` 收口；真机/屏幕阅读器验收仍需执行。
- **1 个布局回归修复**：`v69` 修正会话列表宽度随内容收缩、右栏 composer 过窄，以及卡片动作区与主会话区职责混叠。
- **1 个移动端层级修复**：`v70` 把详情/确认模态提到移动端全屏会话流之上，输入与详情不再被会话流盖住。

原稿的部分结论与当前 `v55` 实现不符，已在本版中撤销或降级；不能继续据此安排开发。

### 1.1 优先级口径

| 级别 | 判定标准 | 处理节奏 |
|---|---|---|
| **P0** | 直接误导核心判断、污染关键计数，或阻塞主任务且无可靠替代路径 | 发布前必须修复 |
| **P1** | 有明确绕行成本，或在常见尺寸/常见失败场景下明显降低可用性 | 下一迭代优先处理 |
| **P2** | 一致性、可理解性、可访问性和长期维护问题 | 随功能迭代收敛 |

## 二、问题与修复方案

### UX-01（P0，已修复待回归）「待处理」已与 `completed` / `waiting` 解耦

> **修复状态**：已在工作区 `v63` 落地，待浏览器/真机回归。  
> **行为验证**：`node backend/scripts/verify-console-attention.mjs` 25/25 通过。

**修复前证据**

- `app.js` 的 `inboxItems()` 只判断 `session.attention` 是否存在，没有排除 `completed`、`waiting` 等非待办状态。
- `updateStats()` 直接用 `inboxItems(nodes).length` 更新「待处理」，导航徽标也复用同一计数。
- `renderAttentionBreakdown()` 把 `completed` 计入「待处理构成」，却完全忽略同样被计入总数的 `waiting`；只有 `waiting` 时甚至不会显示构成面板。
- 线上入口 `#sessions?attention=1` 会把用户带到包含已完成/等待中项的列表。

**影响**

当唯一一条注意力是「已完成」时，页面仍显示橙色「待处理 1」，收件箱也不是空态。当唯一一条是「等待中」时，总数显示 `1`，但「待处理构成」整块不出现，分项里也没有等待中。用户既找不到需要处理的事项，也无法解释这 `1` 从哪里来，统计可信度因此受损。

**修复方案**

1. 在数据层拆成两个概念：`actionableAttention = approval | question | error` 与 `statusAttention = completed | waiting`。
2. 「待处理」、橙色高亮、导航徽标和「需要处理」列表只使用 `actionableAttention`。
3. 「已完成 / 等待中」保留在通知类型和「最近活动」中，不进入待办队列；如需展示，可增加独立的「进行中 / 今日完成」。
4. 待处理构成必须与总数同源、可加总；计数为 0 时，统计卡以中性 0 呈现（辅助文字/`aria-label` 为「暂无待处理」），徽标隐藏；`aria-live` 播报完整语义，例如「1 项待处理」，不要只播报数字。

> 若产品确实把「等待子任务」视为需要用户处理，就必须把 `waiting` 同时加入 actionable 与构成，并统一「待处理 / 需关注」文案；不能保留“计入总数但不展示分项”的现状。

**已落地的实现**

- 新增 `isActionableAttention()`：只认 `approval | question | error`。
- `inboxItems()`、待处理统计、导航徽标、待处理构成和「需处理」筛选统一使用该子集（含已读过滤）；`pendingQueue` 随 inbox 一起收口。
- 移除「待处理构成」里的「已完成」分项；`completed` / `waiting` 继续显示在会话卡片、通知和最近活动中。
- 计数为 0 时统计卡移除链接、取消橙色强调，`aria-label` 为「暂无待处理」，导航徽标隐藏。
- 增加 `verify-console-attention.mjs`，覆盖混合 actionable、仅 completed/waiting、仅 completed、仅 waiting 和「需处理」筛选。

**回归验收**

- 只有 `completed`：待处理为 `0`、徽标隐藏、收件箱为空、无橙色紧迫提示；「最近活动」仍能看到完成记录。
- 只有 `waiting`：待处理为 `0`；若产品希望展示等待中，应出现在「进行中」，不能让总数与构成对不上。
- 同时存在 `approval + completed`：待处理为 `1`，收件箱只出现待审批项。
- 构成各分项之和始终等于待处理总数；点击「待处理」后列表项数量也与统计值一致。
- 增加覆盖上述三种组合的渲染测试。

### UX-02（P1，已修复待回归）会话失败路径已用户化

> **修复状态**：已在工作区 `v63` 落地，待浏览器/真机回归。  
> **行为验证**：`node backend/scripts/verify-console-session-errors.mjs` 18/18 通过。

**修复前证据**

- 原审查在登录态点击会话后看到含 `--web` 的后端原文，右侧详情仍是空态。
- 当前 `v55` 已有 `nodeHasWebUI()` / `openSession()` 前置守卫，但 `webUnavailableText()` 仍返回“启动 aicli 时需带 `--web`”。
- `chatFail()` 仍会拼出「消息加载失败：HTTP 404」一类原始错误。
- 桌面端首次进入会话页不会自动选择会话，`im-chat-empty` 会占据剩余大面积空间。

**影响**

用户点了一个看起来可用的行，却得到开发术语、空白或“无法打开”；既不知道下一步做什么，也无法把诊断信息交给管理员。桌面端空态还会浪费首屏空间，让列表显得孤立。

**修复方案**

1. 在会话行直接显示能力状态，例如「可站内查看」/「仅离线快照」/「网页不可用」，不要等到点击后才失败。
2. 不可用节点不展示「打开原版 Web」；点击会话时打开站内详情的解释态，提供“为什么会这样”“如何修复”和「复制诊断信息」。
3. 把 `--web`、HTTP 状态码等收进可折叠的「技术详情」，主文案改成用户语言。
4. 桌面端首个可见且支持站内会话的会话默认选中；没有会话时保留现有引导空态。
5. 移动端保持“列表 → 会话流 → 返回列表”；浏览器返回键必须回到原筛选和滚动位置。

**已落地的实现**

- `webUnavailableText()` 改为用户语言，不再出现 `--web`。
- 无 Web 的会话卡片显示「网页未启用 / 服务未就绪」，主打开按钮隐藏；卡片点击进入详情。
- 会话详情新增「访问方式」，并提供可折叠「技术详情」和「复制诊断信息」；无 Web 时隐藏不可用的打开按钮。
- 会话面板加载失败显示用户提示，提供「重试」和「复制诊断」；HTTP 状态码与 URL 只进入诊断文本，不进入主文案。
- 桌面首次进入会话页自动选中首个可站内打开的会话；通过 `skipMarkRead` 不把会话误标为已读，且 `skipFocus` 不抢焦点。
- 增加 `verify-console-session-errors.mjs`，覆盖无 Web 卡片/详情、500 加载失败、诊断复制、重试恢复和桌面自动选择。

**回归验收**

- 点击离线、无 Web、版本不匹配三类会话，主界面均不出现裸 `--web` 或 `HTTP <code>`。
- 每个失败态都有明确的下一步动作；诊断信息可一键复制。
- 桌面端有可见且支持站内会话的条目时，不再停留在空白右栏；自动选中不会减少待处理徽标。
- 在 390px 宽度下完成一次“列表 → 会话 → 返回”的往返，筛选与滚动位置不丢失。

### UX-03（P1，已修复待回归）通知设置的核心概念与保存流程不直观

> **修复状态**：已在工作区 `v63` 落地，待浏览器/真机回归。  
> **行为验证**：`node backend/scripts/verify-console-notifications.mjs` 35/35 通过。

**证据**

- 「最低优先级」直接暴露内部枚举：`low（全部）` / `normal（默认）` / `high（仅待审批 / 待回答 / 出错）`。其中“低”反而代表“全部”，与常人理解相反。
- 免打扰是逗号分隔的文本框；虽然有 placeholder，但没有可见格式说明、时间选择器、范围校验和错误提示。
- 未配置的通道仍可能显示为“已勾选但禁用”，视觉上自相矛盾。
- 「保存策略」位于较长的会话覆盖列表之后；页面没有未保存变更提示、导航拦截或 sticky 操作条。
- 会话覆盖列表没有搜索、分组或“仅显示非默认”过滤。

**影响**

用户很容易把“低”理解成“只接收低优先级通知”，或写完非法时段后无反馈。修改一个开关还需要长距离滚动到页尾保存，误离开页面会丢失草稿。

**建议**

1. 不展示 `low` / `normal` / `high`，改为结果导向文案，例如「全部通知」「重要通知（默认）」「仅待处理」；每项配一句触发范围说明。
2. 免打扰改为开始/结束两个时间输入，明确跨午夜规则和时区；非法值就地报错并聚焦。
3. 未配置通道显示为未勾选 +「未配置」标签 + 设置入口/说明，不再使用“勾选但 disabled”。
4. 页面底部改为 sticky 操作条：显示「有未保存修改」，保存按钮只在 dirty 时可用；切换页面或关闭前提示。
5. 会话覆盖增加搜索、按节点分组、「仅显示非默认」过滤；仍保留批量恢复默认。

**已落地的实现**

- 「最低优先级」改为结果导向的「全部通知 / 重要通知（默认）/ 仅待处理」，每项带触发范围说明；会话覆盖同步使用「跟随全局 / 全部通知 / 重要通知 / 仅待处理」，不再展示 `low` / `normal` / `high`。
- 免打扰改为可增删的「开始/结束」时间输入，按网关本地时间计算，明确跨午夜规则；开始等于结束、单边为空、重复区间均就地报错并禁用保存。
- 未配置通道显示为未勾选、禁用，并带「未配置」标签和“需在网关启动参数中配置”的说明；可用通道的开关状态与 muted 语义一致。
- 底部改为固定保存条：持续显示「所有修改已保存 / 有未保存的修改」，仅在 dirty 且校验通过时启用保存；切换页面、退出登录和关闭标签页前提示丢弃草稿。
- 会话覆盖按节点分组，支持搜索（会话名、ID、节点、预览）、「仅显示已调整」和"已调整"标记；列表仍保留批量恢复默认能力。
- 增加 `verify-console-notifications.mjs`，覆盖文案、时段校验、通道状态、dirty/save、导航拦截、搜索/分组/过滤。

**验收**

- 页面中不出现内部枚举值；每个通知范围都有可读解释。
- 输入 `22:00-08:00`、`08:00-22:00`、非法字符串和空值时，均有明确结果与错误反馈。
- 未配置通道不呈现为已勾选。
- 改任意字段后出现未保存提示；保存成功后提示消失；离开未保存页面会二次确认。

#### 修复前实现（问题基线）

| 部位 | 当前做法 | 直接结果 |
|---|---|---|
| 卡片容器 | 三列栅格、左侧 58px 头像位；`tabindex="0"`，但没有明确 `role` | 视觉像列表行，键盘语义却是“可聚焦的 div” |
| 信息层级 | 标题 / 状态徽标 / 时间 → 动态状态 → 摘要 → 节点同步 → 操作区 | 信息层级本身清楚，但操作区单独占一整行 |
| 操作区 | `审批/回答`、`展开`、`打开`、`⋯` 四个槽位；全宽排在卡片底部 | 桌面端 hover/focus 才出现；移动端常显 |
| 按钮尺寸 | 桌面 34px、窄屏 40px；`⋯` 最小宽度 38px | 低于 44px 的舒适触控目标 |
| 弹出菜单 | 在操作区上方绝对定位，包含详情、会话、窗口操作、移除 | 桌面被操作区 `overflow: hidden` 直接裁剪；窄屏也可能越出视口 |
| 离线卡片 | 整张卡 `opacity: 0.55` | 次要文字合成后对比度约 2.47–3.26:1 |
| 展开入口 | `hasExtras` 由 last_message、hasReply、status_tail 任一决定；status_tail 未受全局 `tailEnabled` 约束 | 关闭实时输出且只有尾流字段时会生成空展开 |

当前结构可以概括为：

```text
[头像] 会话标题 [待审批]                 14:32
       摘要 / 动态状态
       节点 · 同步
       [审批/回答] [展开] [打开] [⋯]
                         └─ 菜单向上弹出
```

#### 修复前问题

1. **同一张卡片有三套“打开”语义。**

   | 入口 | 实际行为 |
   |---|---|
   | 点击卡片空白处 | 打开站内会话流 |
   | 点击「打开」 | 打开原版 Web UI（新标签 / 手机上同标签） |
   | 键盘 Enter | 打开「会话详情」弹窗 |
   | 菜单「会话」 | 再次打开站内会话流 |
   | 快捷键 `c` / `o` | 分别打开站内会话 / 原版 Web |

   用户无法从视觉上预测点击会去哪；键盘用户与指针用户得到不同主结果。`打开` 这个标签同时暗示“打开站内会话”和“打开原版 Web”，是最容易误判的一处。

2. **桌面端把关键 CTA 藏在 hover 后面。**

   `.view-sessions .session-card .s-actions` 桌面默认 `max-height: 0; opacity: 0`，只有 hover、`focus-within` 或已展开时才显示。「审批 / 回答」是最高优先级动作，桌面静止状态却完全不可见，违反“不要只在 hover 时露出唯一动作”的交互原则。

3. **多按钮没有稳定主次，移动端操作行过重。**

   普通卡片在移动端常显 2–3 个按钮，待审批/回答时可达 4 个；按钮全部排在底部一行，40px 操作行约等于卡片信息区高度的三分之一。「打开」和「展开」都是同权重 ghost 按钮，主次只有「审批 / 回答」成立。

4. **桌面 hover 造成列表跳动。**

   操作区从 `max-height: 0` 切到 `90px` 并增加 `margin-top`，卡片高度会随指针移动突变；在长列表中，后续行整体位移，键盘焦点也可能在布局变化中变得不稳定。

5. **桌面「⋯」菜单被操作区自身裁掉，且没有翻转和焦点管理。**

   `s-menu` 在操作区内绝对定位并向上弹出，但桌面操作区规则保留了 `overflow: hidden`，且没有在展开态改回 `visible`；因此菜单即使显示也会被操作区裁掉。再叠加 `.im-list-body { overflow-y: auto }`，靠近顶部的卡片会进一步裁剪。菜单只有 `role="menu"`，打开后却不把焦点移入、不支持方向键/Home/End，Escape 关闭后也不把焦点还给触发器。若继续使用 menu 语义，这些键盘行为是必需的；否则应降级为普通 disclosure + 按钮组。

6. **「展开」可能是空按钮。**

   `hasExtras` 直接检查 `status_tail`，但实际渲染尾流的 `tailText` 还受全局 `tailEnabled` 控制。用户关闭实时输出、且该会话只剩 `status_tail` 字段时，展开按钮仍会出现，点击后却没有新增内容。展开可见性应由“展开后实际会出现的块”计算，而不是由原始字段猜测。

7. **离线卡片用整卡透明度换状态，代价是不可读。**

   `opacity: 0.55` 同时压暗标题、摘要、状态和操作。以暗色列表底色估算，`--fg-faint` 约 2.47:1、`--fg-muted` 约 2.93:1，低于 4.5:1。离线应使用徽标、虚线轨道或背景去饱和，不应降低整卡文字对比度。

**影响**

桌面鼠标用户可能点了「⋯」却看不到详情、窗口操作和移除；审批/回答又被 hover 隐藏，实际可发现的动作只剩不明确的「打开」。窄屏用户则要为每张卡片承担 2–4 个按钮和约 40px 的操作行。结果是高频打开会话反而不如低频管理动作显眼，且离线卡片难以扫读。

#### 已采用的目标结构

目标不是把按钮做得更小，而是建立“**一个主路径、一个上下文动作、一个溢出菜单**”的稳定模型：

```text
普通：
[头像] 会话标题                         14:32
       摘要 / 动态状态
       节点 · 同步
       [打开会话] [⌄] [⋯]

待处理：
[头像] 会话标题 [待审批]                14:32
       摘要 / 动态状态
       节点 · 同步
       [审批] [⌄] [⋯]
```

- **卡片点击与主入口 Enter 必须进入同一个站内会话**；不再让 Enter 去详情。
- 普通状态只保留一个「打开会话」主按钮、一个可选展开 chevron 与一个 `⋯`；待审批/回答时，主按钮替换为「审批/回答」。
- 「原版 Web」在菜单中明确命名，不再使用含糊的「打开」；只有无站内面板的旧版节点把它作为显式主按钮回退。
- 菜单移除重复的「会话」项；保留「详情」「原版 Web」「新终端」「恢复」「关窗口」「移除」。
- 「展开」改成动作区内的轻量 chevron，仅在确实存在可展开内容时出现，不再占一个完整文字按钮。
- 桌面端不使用 hover 才显示动作区；「⋯」和上下文主按钮常显，避免卡片高度变化。窄屏主按钮与「⋯」都保持至少 44×44px。
- 菜单改用 fixed 视口定位并做上下翻转；打开后聚焦第一项，支持方向键、Home/End，Escape 关闭并把焦点还给「⋯」；滚动/窗口变化时重新定位。
- 卡片补充 `role="group"`、清晰的可访问名称和真实「打开会话」主按钮；整卡 focus 保留用于 `j/k` 与 Enter 主路径，空白点击委托到同一动作。
- 离线快照去掉整卡 `opacity`，改用「离线快照」徽标、虚线轨道和局部弱化；正文与操作文字保持 AA。

#### 已落地的实现

- `data-open` 主入口统一调用 `openSessionFromCard()`：有站内面板进站内会话，仅旧版 Web 节点落原版 Web，无 Web 路由进详情；卡片的指针点击、Enter、`c` 快捷键共用该路径。
- `data-web` 取代重复的「会话」菜单项；原版 Web 不再和站内打开共用「打开」文案。
- 动作区常显，普通卡片为「打开会话 + 展开 chevron + ⋯」，待处理卡片为「审批/回答 + 展开 chevron + ⋯」；窄屏 44px。
- `⋯` 菜单改为 fixed 视口定位与上下翻转；打开后焦点进入首项，支持方向键/Home/End，Escape 归还焦点，滚动或窗口变化时重新定位。
- 展开可见性改为 `last_message || wantReply || tailText`；实时输出关闭时不会出现空展开。
- 会话卡片不再整卡降透明度；离线状态保留徽标与弱化头像，正文对比度恢复。
- 控制台资源版本提升到 `v63`，避免 Service Worker / CDN 继续命中旧菜单。

#### 回归验收

- Web 可用时，点击卡片、点击「打开会话」、在主入口按钮/链接上按 Enter，三者进入同一站内会话；键盘与指针行为一致。
- 站内面板可用时，「原版 Web」只出现在菜单中；旧版 Web-only 节点的主按钮必须明确写作「原版 Web」，不再出现两个都叫「打开」但目标不同的动作。
- 桌面静止、hover、键盘聚焦三种状态下，卡片高度和列表位置不变化；审批/回答 CTA 不需要 hover 就能看到。
- 390px 下普通卡片最多两个常显文字动作（主按钮 + `⋯`）；展开 chevron 仅在有内容时出现，触控区同样不小于 44px，待处理卡片主按钮不换行、不横向溢出。
- 桌面点击「⋯」必须真正看到完整菜单，不能再被 `.s-actions` 的 `overflow: hidden` 裁掉；第一张和最后一张卡片的菜单在 390px、768px、1568px 下都完整落在视口内。打开后焦点进入菜单，Escape 后回到「⋯」。
- 只有实际存在最后消息、在线可回复输入或已开启的实时尾流时，才显示展开 chevron；点击后必须出现新内容。
- 离线卡片的标题、摘要和操作文字实测对比度不低于 4.5:1。
- 用键盘完成：Tab 进入「打开会话」→ Enter 打开会话 → 返回列表 → Tab 到「展开」→ Space 展开 → Escape 退出菜单；全程焦点可见。

### UX-10（布局回归，`v69` 已修复）会话列表宽度、composer 与动作归属

**用户反馈**

- 会话区域宽度每次都在变化；
- composer 输入框过窄；
- 列表卡片仍把「打开 / 审批 / 展开 / 详情 / 窗口」堆在标题附近；
- 桌面端这些动作应在主会话区，移动端只保留摘要列表。

**根因**

1. `.views` 同时是 flex 子项且设置 `margin-inline:auto`，没有显式 `width:100%`，浏览器把它收缩到内容宽度；
   1440px 下实测 `.im-app` 只有 861px，右栏自然变窄，composer 随之变小。
2. `.session-table` / `.group-body` 继承了早期网格布局的 `align-items:start`；改成 flex 后，
   卡片按内容宽度收缩，标题/徽标长度变化就会让列表宽度跳动。
3. 卡片动作区仍常驻：卡片同时承担“选择会话”和“会话管理”，与右栏会话流职责重叠。
4. composer 使用 flex + 文字发送按钮，输入框的 flex-basis 受内容和按钮宽度影响。

**已落地实现**

- `.views` / `.app-views` 显式 `width:100%`；`.im-app` 固定 `304px + minmax(0,1fr)`；
  `.session-table` / `.session-group` / `.group-body` 全部 `align-items:stretch`，卡片 `width:100%`。
- 列表卡片只保留身份行、动态状态、摘要、元信息；`.s-actions`、`.s-last`、`.s-reply`、`.s-tail`、
  `.s-live` 在会话列表内隐藏。卡片点击、Enter、Space 统一打开主会话区。
- 右侧会话头新增 `#chat-more` / `#chat-more-menu`：详情、原版 Web、新终端、恢复、关窗口、移除。
  审批/回答仍由会话流交互区承载，不再出现在列表卡片。
- 会话头移除原来的「打开原版 Web」「详情」两个独立按钮，降低标题区拥挤。
- composer 改为 `grid-template-columns: minmax(0,1fr) auto`；输入框 `width:100%`，发送按钮改为
  图标 + 可访问名称，不再用文字挤占输入宽度。
- 移动端保持摘要列表 + 全屏会话流；动作统一在会话头菜单，卡片不再显示动作行。
- 移动端会话流 `z-index:60`；详情/确认等 `.modal-scrim` 提升到 `70`，toast 提升到 `80`。
  390×844 层叠探测中 `elementFromPoint(中心)` 命中 `modal`，不再被会话流遮挡。

**真实布局验证（Edge headless + 静态 harness，`v69`）**

| 视口 | `.im-app` | 列表 | 会话流 | composer 输入框 | 卡片动作 |
|---|---:|---:|---:|---:|---|
| 1440×900 | 1192px | 304px | 886px | 816px | `display:none` |
| 1024×768 | 776px | 304px | 470px | 400px | `display:none` |
| 390×844 | 362px（列表整页） | 362px | 390px（全屏） | 316px | `display:none` |

**行为验证**

- `verify-console-chat-panel.mjs` 44/44：固定轨道、显式宽度、composer 网格、卡片摘要化、
  会话头菜单与焦点行为。
- `verify-console-danger.mjs`：窗口动作已从卡片迁移到会话头菜单。

 ### UX-06（P2，已实施待回归，`v67`）危险操作层级收敛
 
 #### 现状证据

 - **MCP 挂载页** (`app.js:2601`)：「删除」挂载使用实心红。
 - **节点离线快照** (`app.js:2266`)：「移除」节点为红色按钮；**会话列表卡片菜单** (app.js:1684-1685)：「关窗口」「移除」为红色菜单项。
 - **仪表盘离线面板** (index.html:335)：「清除全部」为独立红色按钮。
 
 #### 影响
 
 用户浏览时，红色在第一眼就被识别为「高优先级/危险」。窄屏换行后，误触风险增加。同时，这些操作缺乏统一的后果说明与确认流程。
 
 #### 建议改法
 
 1. **列表行默认移除红色按钮**：收进 `⋯` 菜单或页面级「危险区」。
    - 令牌/MCP/节点卡片的撤销/删除进入各自卡片的溢出菜单。
    - 会话卡的「关窗口」「移除」已在 v63 进入菜单，但仍未加二次确认。
 2. **二级确认策略**：
    - 可恢复动作（如单条令牌撤销）→ 描边危险样式 + 弹窗确认（文案包含对象、数量、后果）。
    - 不可恢复批量动作（如「清除全部」离线快照）→ 「标题 · 溢出菜单」进入 + 二次确认页或模态框。
 3. **反馈与焦点恢复**：确认后焦点返回触发器，提供 toast 成功/失败提示。

 ### UX-07（P2，已实施待回归，`v68`）信息层级冗余收敛

 #### 影响

 #### 建议改法
 
 1. **每页只保留一个页面标题**：H2 统一在 `<main>` 内第一行，内容区用描述性副标题（如「已注册连接器」），不要和导航项同名。

 3. **技术字段降级**：实现术语放入「高级信息」或可展开详情；原始值保留供复制。
 4. **事件条限高**：默认最多 3 chip +「还有 N 条」，点击展开历史；已完成事件不进入全局事件条；与「最近活动」去重。
 5. **内容最大宽度**：`.views` 增加 `max-width: 1440px; margin-inline: auto;`。
