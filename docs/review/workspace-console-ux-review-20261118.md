## 三、P0 阻断级问题

### P0-1 右侧栏是模态覆盖层，打断"读产物 → 改指令"的核心循环

**现象** [实测]
- 右侧栏的可访问性身份是 `dialog "右侧栏（覆盖层）" modal`，带遮罩
- 展开后主区（消息流）整体变暗、不可读；点击输入区会**直接关闭整个右侧栏**

**为什么这是 P0**
Agent 的真实工作循环是：看它产出的文件/计划 → 觉得不对 → 立刻补一句指令。当前设计里这个循环被强制切成两段：
你要么看产物（输入区被遮罩、点一下还丢面板），要么写指令（产物看不见）。
而且重新打开后虽然页签选中态会保留，但**你的视线位置和对照关系全部丢失**——需要再次滚动定位到刚才那个文件。

**建议**
1. 桌面端（≥ 1280px）改为**非模态停靠区（docked aside）**：主区用 `flex` 收缩，不加遮罩，输入区始终可用。
2. 窄屏（< 1024px）才退化为覆盖层，且覆盖层出现时**底部输入区应保持在遮罩之上可见可编辑**。
3. 覆盖层关闭方式统一到"点遮罩 / Esc / 关闭按钮"三种，且关闭后焦点回到展开按钮。

**定位**：`components/workspace/artifact-panel.tsx`（容器与覆盖层实现）、`components/workspace/panel-registry.ts`（页签注册源）

**验收**
- 右侧栏展开状态下，输入框可直接聚焦输入，发送按钮状态正常翻转
- 展开状态下消息流保持正常亮度、可滚动阅读
- 关闭后焦点回到"展开右侧栏"按钮

### P0-2 宽度分隔条是"假抓手"

**现象** [实测]
分隔条的语义为 `调整右侧栏宽度, value=320, valuemin=320, valuemax=320`。
即：它渲染成可拖拽的样子（`cursor: col-resize`），但可用区间为零——**怎么拖都不会变**。

**为什么这是 P0**
假交互比没有交互更伤信任。用户会连续拖 3–5 次试图把产物区拉宽（因为下面 P0-3 正说明它太窄），全部无效后开始怀疑页面卡死。

**建议**
1. `valuemin = 320`，`valuemax = 720`（或 `min(50vw, 760)`），拖拽过程实时反馈宽度提示。
2. 宽度持久化到 `localStorage`，切会话不重置。
3. 二次点击分隔条可折叠/展开（比拖到最窄更好用）。
4. 如本版本不打算支持调宽，则**直接移除该分隔条**，不要保留假抓手。

**验收**：拖拽 320 → 640 → 720 三档均生效；刷新后宽度保持；双击可折叠。

### P0-3 9 个页签在 320px 宽内折成 4 行

**现象** [实测 + 源码]
页签序列（来自 `panel-registry.ts`）为：
`条目 / 计划 / 还原 / 文件 / Git 变更 / 自动化任务 / 会话详情 / 会话 MCP / 计划归档`
在 320px 宽度下折为 **4 行**（2 / 3 / 3 / 1 分布），并吃掉右侧栏约 30% 的垂直空间。

**具体问题**
- 折行后每行按钮宽度不等，"条目"独占一行、末行仅 1 个，"计划归档"像被孤立出来
- 首行"条目"与面板标题"文件产物"语义重复
- 9 个页签平铺，没有任何分组线索（产物类 / 会话类 / 运维类混排），扫读成本高

**建议**
1. **一等公民只留 3 个**：`条目 / 文件 / Git 变更`（并支持按当前会话状态动态置顶，例如有未提交改动时 Git 变更有徽标）。
2. 其余 6 个进 `更多 ⋯`，或在 `更多` 里按分组呈现：
   - 产物类：计划、计划归档、还原
   - 会话类：会话详情、会话 MCP
   - 运维类：自动化任务
3. 页签条改为**单行横向滚动**（`overflow-x-auto` + `scroll-snap`）+ 两侧出现渐隐/滚动箭头，**禁止 `flex-wrap` 折行**。
4. 页签加计数徽标（计划 n 条 / Git 改动 n 个），减少"盲点式点开再看有没有"。
5. 极窄场景（< 400px）改用"下拉选择器 + 内容区"替代页签条，彻底释放纵向空间。

**验收**：在 320 / 480 / 720px 三个宽度下，页签区高度恒定且为单行；`更多` 内 6 项均可达。

## 四、P1 高优先级问题

### P1-1 浮层不互斥：输入菜单与模型/权限面板同时展开

**复现路径** [实测，稳定复现]
1. 点输入框左侧"输入菜单"→ 命令面板展开
2. 不关闭，直接点"模型与推理"→ **面板展开，但输入菜单仍处于展开态**，两层浮层叠在一起，模型面板还把输入框本体压住
3. 同样的情形出现在"权限"：权限下拉与输入菜单同时展开，权限下拉的定位又压住了模型控件

**根因** [源码]
`message-composer.tsx` 中 `ComposerMenu`、`ComposerModelPanel`、`permissionModeControl`、`profileControl`、上下文用量弹层各自持有独立开关，没有统一仲裁者。

**建议**
引入**单一互斥枚举**：`type OpenSurface = null | 'menu' | 'model' | 'permission' | 'profile' | 'context'`，
任何一次打开都把其余置 `null`；同一时刻最多一个 `expanded=true`。
另外所有浮层的 `z-index` 与锚点需统一：**面板不得覆盖输入框本体**（应向上展开并让输入框保持可见），锚点优先左对齐到触发按钮。

**验收**：断言任意时刻 `document.querySelectorAll('[aria-expanded="true"]')` 里浮层类不超过 1 个；模型面板展开时输入框仍完整可见。

### P1-2 输入菜单"铺满全宽但只填左半边"，且一半分组需要滚动

**现象** [实测 + 源码]
菜单容器为 `absolute bottom-full left-0 right-0`（`composer-menu.tsx:44`），即**强制等于输入框全宽**；
但内容仅单列左对齐，右侧约 60% 是纯空白，视觉上像"渲染没完成"。
同时 `max-h-[18rem]` 下，默认只能看到 `命令`、`操作` 两组，`技能`、`文件` 两组落在滚动区外。

**为什么难受**
`技能`（8 项）和 `文件`（1 项）是本产品最具差异化的两个入口，默认不可见等于默认不存在；
而占据首位的"命令"组有 6 条 `/xxx`，属于低频高级用法。

**建议**
1. 宽度改为**内容自适应**（`w-[min(480px,100%)]`）或双列栅格；不要 `left-0 right-0` 铺满。
2. 分组排序改为**按使用频率**：`操作（添加附件）` → `技能` → `文件` → `命令`；
   或每组只展示前 4 条 + 组内"查看全部 6 条命令"。
3. 高频命令（`/model`、`/rename`）可从菜单中移除——它们在底部工具栏已有等价控件，避免双入口。
4. 底部快捷键提示（`↑/↓ 选择 · TAB 展开…`）当前用 `app-text-9 uppercase tracking-[0.12em]`，中文界面下字号过小且字距被拉开，改为 `app-text-10` 常规字距。

**验收**：打开菜单**无需滚动**即可看到全部 4 个分组标题；菜单宽度不再铺满输入框。

### P1-3 模型控件"点了没反应"

**现象** [实测]
同一按钮（底部"magpie · auto/deepseek-v4.1-flash-1017 · max"）连续点击 **3 次**：
第 1、2 次**页面无任何变化**（无 pressed 态、无面板、无 loading），第 3 次才展开面板。

**为什么必须修**
这是全页最核心的两个控件之一。"点击无反馈"在 2 次之后用户就会判定为 bug 并放弃，比"点错"更致命。

**建议**
1. 排查该按钮上方是否存在透明拦截层（同层浮层、`pointer-events` 残留、`aria-hidden` 但未 `display:none` 的浮层）。
2. 命中区扩到 ≥ 32×32，并给 `:active` / `expanded` 明确的视觉反馈（按下去要有变化，100ms 内）。
3. 面板渲染加上 `onMouseDown` 前置打开，避免与 `blur` 关闭产生竞态（点击时"开了又立刻关"的典型成因）。

**验收**：连续点击 5 次，5 次均在同一帧内出现面板或明确按下态。

### P1-4 "跳过权限校验"作为常态默认项，危险信号被稀释

**现象** [实测 + 源码]
底部常态显示：`权限 · 跳过权限校验 ⚠`，其说明为"全部工具调用直接放行，仅在可信工作区使用"（i18n `workspace/base.ts:431`）。
在视觉上，它与右侧"Profile 默认"、左侧模型胶囊**同色、同字号、同粗细**，只有一个很轻的 ⚠。

**问题**
- 这是**全系统风险最高**的一个开关，却排在常规设置项中间，扫读时会被当成普通标签滑过
- 默认就落在最高危档，用户没有任何"我主动选择了危险"的确认感
- 与"上下文 <1%"这类纯信息项混在同一行，信息与操作、安全与状态没有分层

**建议**
1. 危险态使用**语义色**（红/琥珀）描边 + 实心图标，与"默认/允许"形成一眼可辨的差异。
2. 会话新建时默认落在安全档；从安全档切到"跳过校验"必须经过二次确认（仓库里已有 `permission-mode-confirm-dialog.tsx`，请确认该确认是否真的挂在了切换路径上，而不只是组件存在）。
3. 处于危险档时，在消息区顶部常驻一条**可关闭的警示条**（比按钮里的小字有效得多），点击可直达切换。
4. 把"权限"从这排胶囊里提出来，单独成一个有边界的区域（例如与发送按钮同一视觉组），表明它是"提交时的策略"而非"附加信息"。

**验收**：三种权限态在同一位置可一眼区分；从安全档切换到危险档出现确认；危险档下消息区顶部有警示条。

### P1-5 左侧目录行：一行挤 3–4 个无标签图标

**现象** [实测]
同一个目录行上并排出现：
`添加目录` / `工作目录段操作`（popup: dialog）/ `目录操作`（popup: menu）/ `注册并在该目录下新建会话`

**问题**
- 全部是无文字图标，语义只能靠 `aria-label`（视觉用户看不到）
- 其中"注册并在该目录下新建会话"与目录行的新建入口语义重叠，且按钮名称冗长到无法做成图标
- 两个同类操作却分别打开 `dialog` 和 `menu` 两种不同 popup 类型，交互模型不一致

**建议**
1. 目录行默认态**最多 2 个可点元素**：目录名本身（切换/展开）+ 行尾 `⋯`。
2. `⋯` 菜单内收敛为：`在此外新建会话` / `在此搜索` / `重命名目录` / `从工作区移除`。
3. 高频的"在该目录新建会话"改为**悬停时浮出的 `+`**（仅在 hover/focus 时出现，静止态不占位置）。
4. 统一 popup 类型：行级操作一律用 `menu`，真正需要收集多个字段的才用 `dialog`。

**验收**：目录行静止态可点元素 ≤ 2；所有行级操作有中文文字标签（菜单内）。

### P1-6 同一区域并存两个搜索入口

**现象** [实测]
`搜索线程`（searchbox）与 `打开会话检索`（button）紧邻出现。

**问题**
用户无法判断差异（一个过滤当前列表？一个全局检索？）。两个入口并列时，人会选错，然后认为"搜不到"。

**建议**
合并为一个输入框：`⌘K` 聚焦，输入即**过滤当前目录下的会话**；输入后若想全库检索，在结果列表底部给一条显式出口
`在所有 136 个会话中搜索 "xxx" →`。删除并排的第二个按钮。

**验收**：左导航只保留一个搜索输入框。

### P1-7 会话被目录折叠吞掉，回到旧会话路径过深

**现象** [实测]
`ai-agent-runtime` 目录下 34 条会话，默认只露 5 条，其余收在 `展开其余 29 个会话`；
同屏还有 `sap_network_core 23`（同样折叠 18 条）等十余个目录，总计 136 个会话。
时间戳粒度混排：`3分钟前` / `19小时前` / `前天` / `3天前`。

**问题**
- "回到昨天那个会话"需要：找目录 → 展开 → 再扫列表，3 步以上
- 目录优先的层级假设了"用户按项目回忆"，但真实回忆线索通常是**"什么时候做的"**或"当时在聊什么"
- 时间字符串宽度不一，纵向扫读时无法对齐，进一步降低速度

**建议**
1. 一级分组改为**时间维度**（今天 / 昨天 / 本周 / 更早），目录降为会话项上的次级标签。
2. 每个时间组默认 10 条，组内保持目录分组；目录级给一个粘性的"在当前目录内搜索"。
3. 增加**收藏/置顶区**（放最上，1 次点击可达）。
4. 时间统一右对齐并用固定宽度槽位（`3 分钟前` / `19 小时前` / `2 天前`），保证纵向对齐。
5. 会话项补充一条次级信息（模型名或首条消息摘要），解决"会话名与目录同名"（如目录 `ai-agent-runtime` 与会话 `ai-agent-runtime` 并存）无法区分的问题。

**验收**：回到"昨天的某个会话"≤ 2 次点击；时间列右对齐宽度一致。

## 七、建议落地顺序

### 第一批（1–2 人日，纯前端，收益最高）
- 浮层互斥状态机（P1-1）
- 右侧栏分隔条 min/max + 持久化，或移除假抓手（P0-2）
- 模型控件命中与竞态修复（P1-3）
- 输入菜单宽度与分组排序（P1-2）
- 文案替换（P2-1 ~ P2-4），集中改 i18n 资源

### 第二批（3–5 人日，结构改造）
- 右侧栏停靠化（P0-1）
- 页签精简为 3 + `更多` 分组，单行滚动（P0-3）
- 权限危险态视觉分层 + 切换二次确认 + 警示条（P1-4）

### 第三批（1–2 周，信息架构）
- 左导航改为时间分组 + 收藏区 + 单行主操作（P1-5 / P1-7）
- 合并双搜索入口（P1-6）
- 顶部工具栏收敛（P2-8）

**每批建议配套 e2e 断言**（可复用现有 vitest 体系）：
1. 任意时刻可见浮层 ≤ 1
2. 320/480/720px 下页签区高度恒定
3. 右侧栏展开时输入框可聚焦（`toBeEditable`）
4. 拖动分隔条后宽度变化并被持久化

**审查结论**：当前页面"看起来"已经是一个成熟的深色工作台，但**操作层面的骨架还没跟上视觉进度**——
最关键的三个断点（右侧栏模态化、浮层不互斥、页签过载）都发生在用户每天要重复几十次的动作上。
建议按第七节分三批推进，第一批 1–2 人日即可消除"点了没反应""面板叠面板""拖不动"这三类最伤信任的体验缺陷。
